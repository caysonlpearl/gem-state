# Website personalization and shopping follow-ups

Signup has required versioned Terms acceptance and one optional shopping-email/website-notification opt-in. Google onboarding records the same choices. Broader permission defaults off for existing members. Existing saved listings and requested saved-search alerts remain independent until an explicit all-shopping unsubscribe or account alert-off action. There are no frequency tiers or daily email caps.

## Release order and switches

1. Apply `20261113010000_shopper_personalization.sql` to GemList in a transaction after confirming the project and backup. It creates private, RLS-protected tables/functions and additive source-verification/notification guards. It does not backfill private browsing or opt anyone into broader email.
2. Deploy the app and verify signup, privacy withdrawal, account switching, and the private `/admin/shopping` report. Tracking, recommendations, embeddings, and weekly evaluation default enabled; shopping delivery and advertising initially remain paused.
3. Run the protected shopping sweep to build the full eligible native/catalog projection. It uses cached provider reads only; the initial catalog is not treated as new saved-search matches. Native, dealer-feed, and API completeness/availability/moderation gates remain authoritative. Missing records expire as candidates; they are never labeled sales.
4. Configure the independent public-content embedding runner. Add one identical random `SHOPPING_JOB_SECRET` to web-host secrets and the repository Actions secret, then set repository variable `SHOPPING_EMBEDDINGS_ENABLED=true`. Run `Shopping listing embeddings` manually once; its hourly schedule processes changed hashes only. It checks for work before installing/loading the model. Do not put SigLIP on the 1 GB inventory VPS.
5. Enable Shopping delivery in Admin → Analytics → Shopping performance after queue/availability/unsubscribe verification. The `bluebird-shopping` database schedule invokes the shared worker every 15 minutes using the existing authenticated job credential. The saved-search entry point delegates to the same leased worker. Related candidates within a processing window share one durable delivery; distinct windows can send on the same day.
6. Optional advertising remains paused until actual Meta/Google credentials are configured and validated. `META_PIXEL_ID`, `META_CONVERSIONS_TOKEN`, `GOOGLE_MEASUREMENT_ID`, and `GOOGLE_MEASUREMENT_SECRET` are server configuration. Only the consent-gated Meta Pixel loads in the browser; Google uses the allowlisted server adapter. Do not add automatic URL/search/form capture. Meta shares event IDs across browser/server; Google events use one server path and are not retried after an ambiguous handoff. Verified purchases use transaction IDs.
7. Register the signed Resend webhook `/api/shopping-email-events` and set `RESEND_SHOPPING_WEBHOOK_SECRET` before treating provider complaints/bounces as complete. Clicks and approximate opens work independently. Existing operational email remains separate.

Each switch is independent, including embedding compute and weekly ranking evaluation. Pausing does not delete saved listings. The web-host and repository secrets must never be committed or returned in reports.

## Ranking and reminders

SigLIP 2 public text/photo features are generated by the pinned `google/siglip2-base-patch16-224` checkpoint and stored as versioned 768-dimensional vectors. The worker averages normalized text/image representations and normalizes the result; unavailable photos fall back to text. Candidate vectors stay in Postgres and HNSW candidate retrieval returns only public cards/similarities. Stale hashes are excluded. There is no LLM.

Signal weights live in `SHOPPING_WEIGHTS`. Default verified purchase/inquiry/favorite/repeat/search/view weights are 20/12/10/3/2/1, with a 14-day half-life, 30-day profile window, and persistent explicit favorites. Category and home shopping mode remain separate. Explicit browse filters/sorts retain their existing authority. Private messages, identity records, and payment credentials never enter vectors or advertising.

Qualifying unchanged-item reminders start at 24 hours, 72 hours, and seven days after a favorite or repeat visits in two sessions within a seven-day window. A cycle cannot resend the same step without fresh activity. Contact pauses it seven days; purchases, dismissals, unavailability, and withdrawal suppress it. Repeated unanswered reminders are reduced independently of genuine new changes. Bluebird controls timing; these settings are not represented as competitor schedules. There is no mandatory digest.

Weekly challengers train on bounded, normalized recommendation features and source-verified inquiry/purchase outcomes. Training and evaluation split by shopper. Promotion needs at least 200 training pairs, 100 test pairs, 30 shoppers with verified outcomes, and a three-point held-out pairwise accuracy improvement. These are offline ranking checks, not a promised conversion lift. A stable 10% comparison group evaluates shopper contacts and return behavior; it keeps explicit alerts and history tools.

## Delivery and privacy guarantees

Queue uniqueness is per shopper/listing/source event. Delivery leases, recipient serialization, provider idempotency, capped retries, and per-window grouping protect against duplicates. Verified email recipients only; managed imports and synthetic addresses are excluded. Permission, individual saved searches, availability, prices, dismissals, and contacts are checked again after email rendering, immediately before provider handoff. Already accepted email cannot be recalled.

Unsubscribe is a signed-recipient-token POST with one-click headers; GET shows confirmation to avoid link-scanner unsubscribes. It atomically updates preference audit/suppression. Consent withdrawal and event writes serialize in Postgres so an in-flight batch cannot restore history. Accounts cannot read other shoppers' history, vectors, queues, consents, or analytics. Browser-characteristic hashes never establish identity or merge accounts. Precise coordinates are transient and excluded from private activity/ad payloads. Global Privacy Control suppresses advertising.

Browsing/search events expire after 90 days; recommendation profiles use 30. Explicit saves stay in their original systems. Delivery/dedup records expire after 180 days, provider outbox records after 30. Durable dismissal, trusted purchase stops, and completed reminder steps persist independently until history is cleared or consent withdrawn; guest choices expire with the guest privacy record. Email pixels are approximate; actual clicks/contacts are stronger outcomes.

## Capacity and verification

`/admin/shopping` reports current catalog/vector counts, activity/vector bytes, queue outcomes, opt-outs, provider complaints, cohort contacts, and weekly evaluations. No feature is evidence of a verified sale unless a trusted order capture or live verified-sale record exists. Inferred inventory disappearance never supplies purchase evidence.

Embedding compute is isolated from the website and inventory VPS. Jobs are bounded to 35 minutes of work/45-minute runner lifetime and 32-item writes. Model/checkpoint caches avoid repeat compute; idle runs skip model installation/loading. Catalog/notification writes and availability reads are batched. Measure actual database/vector growth and worker execution before increasing throughput. Existing listing-provider budgets are unaffected by recommendations, similarity reads, alerts, and embedding jobs.

Validation: production code tests cover browser event allowlists, trusted purchase isolation, filtering, ranking, reminder thresholds, RLS, consent audit/withdrawal, preserved saved alerts, retry deduplication, multiple deliveries per day, recipient handoff races, and rendering-time unavailability. PGlite tests substitute array distance for pgvector/HNSW; validate the actual extension/index on production or a real pgvector database before enabling vector retrieval.

Sources: [SigLIP 2 model](https://huggingface.co/google/siglip2-base-patch16-224), [Transformers SigLIP 2 documentation](https://huggingface.co/docs/transformers/model_doc/siglip2), [Google Measurement Protocol](https://developers.google.com/analytics/devguides/collection/protocol/ga4/reference).

## Favorite authority and removals — November 14, 2026

Signed-in favorite state now comes from the actual member watchlist and saved
partner vehicles/homes/jobs through the existing private
`shopping_saved_interests` read. A delayed analytics save or an obsolete
`shopping_favorites` row cannot recreate a removed bookmark's favorite boost.
Historical save events contribute only while that reference is actually saved;
member unsave events no longer act as a second bookmark database. Legitimate
views, contacts, trusted outcomes and requested saved searches keep their own
meaning. Current saves retain their original reminder anchor, including a later
real save event; removing and genuinely saving again creates renewed interest.
History clear keeps real bookmarks while excluding older optional interests.

Delivery checks load complete sent-reminder progress and history before taking their final recipient, queue, search and inventory snapshots; a withdrawal during a slower history read also suppresses discretionary alternatives. Sent steps use the same bounded, exact-count pages and ownership checks as durable choices. A capped or malformed ledger is unavailable, never treated as permission to repeat an older reminder.

The reader validates the subject, checks personalization/deletion state before
and after the read, and discards the earlier snapshot if permission/history
changes. Its existing 1,500-event browsing sample now uses deterministic pages
rather than silently inheriting a 1,000-row API cap. Current saves and durable
choices are complete, exact-count reads in 500-row pages, with a 5,000-row review
ceiling. A single eight-second deadline, disabled SDK retries, stable counts,
duplicate/owner checks and explicit source errors prevent incomplete reads from
falling back to stale favorites. Bookmark truth is fetched after history/choice
pages so a removal during slower reads is visible to the subsequent delivery
check. No provider request or model inference is added.

Price-drop generation and immediate provider-handoff checks require current
positive interest as well as a confirmed current price change. A removed
favorite alone no longer qualifies. Independent browsing can still qualify;
removing a favorite is not a general shopping unsubscribe. Requested matching
alerts keep their separate permission/search checks. Once a provider has
accepted a message, later changes cannot recall it.

Member activity stops writing the redundant favorite cache; guest behavior is
separate. Migration `20261114140000_prune_member_favorite_cache.sql` only prepares
a service-only cleanup function. It is not installed or executed on production.
After publishing/verifying the authoritative reader, an operator can retire
recognized member-cache rows in batches of at most 100. Each brief operator transaction holds a schema/write lock and refuses unreviewed children, deletion hooks, rules or inheritance before touching data. `remaining: true`
includes rows locked by another transaction, so a zero-deletion batch is not
proof of completion. Guest favorites, actual bookmark tables, history, choices
and unrecognized subjects are preserved; unknown subjects require separate
review. No cleanup scheduler or deletion worker is enabled. The runtime fix
uses the already-installed saved-interest RPC and does not depend on this
cleanup migration.

Synthetic tests reproduce the former ghost-favorite behavior, execute the real
bookmark RPC against member/partner records, cover removal/resave, anchors,
multiple accounts, unavailable asks, paginated saves/choices/history, malformed
or capped reads, privacy changes, guest isolation and stalled bodies. Delivery
fixtures remove a bookmark during rendering and verify no provider handoff.
The real two-connection PostgreSQL gate verifies locked-cache skipping,
remaining-work reporting, preserved guest rows and unchanged deletion-boundary
coverage. These are source/fixture checks, not production-member or physical
phone journey evidence. No real bookmark, optional record or email was changed.

## Category-aware recommendation context — November 15, 2026

The shared web/app service now selects its eight visual seeds across category
and home-intent groups before taking a second seed from one group. The agreed
signal weights, decay, explicit search filters/sorts and stable comparison
assignment are unchanged. A dominant vehicle interest can no longer occupy
every seed slot while a separate furniture or home interest is present.
Exposure model names append `:category-seeds-v1` to identify this candidate
selection change; it does not promote a trained ranking challenger or change
the embedding model.

Recently viewed follows actual detail-view chronology within the recommendation
window. It no longer depends on the eight strongest visual seeds or inclusion
in the newest 200 public inventory rows. Continue shopping resolves its own
favorite/repeat-visit references, including older explicit favorites. Saves and
purchases do not manufacture detail views. The union requires at most 24 full
reference cards; availability, publication, native catalog restrictions and
external-cache eligibility still apply before returning them. Missing vectors
do not block history, and public discovery remains the failure/cold-start
fallback.

Category/home-mode context is reused from the existing public pool and native
eligibility reads. Only missing contexts require an additional metadata lookup
against `shopping_inventory`, projecting `listing_id`, `category` and home mode
without listing text/photos or new provider requests. It supports the existing
bounded history/favorite/choice budgets with a 15,000-id ceiling, URL-sized
chunks, at most four concurrent reads, an eight-second deadline and no SDK
retries. Exact counts distinguish missing inventory from a capped response.
Missing inventory is omitted; malformed, foreign, duplicate or partial
failed results reject the lookup rather than silently returning a different
personalization profile. Sibling requests settle under cancellation.

Before returning personalized rows, the service rechecks permission and the
original immutable history cutoff. Withdrawal, deletion-pending state or a
history clear during slower candidate reads discards that earlier snapshot.
This change adds no tracking fields, consent scope, SDK, migration or paid
capacity. Native terms, personalization and advertising controls stay separate.

A read-only production cache measurement used its primary-key index for 200
category/home-mode projections: 164.79 ms execution, 11.816 ms planning, 233
shared-hit blocks and zero shared-read blocks. This is one database sample,
not end-to-end request latency or a load test. It read public cached inventory,
not member histories. Source evidence is under
`output/shopping-interest-context-20261115/`. Focused tests execute the real SDK
projection against PostgreSQL JSON fields, bounded transport/error handling,
category/home-intent coverage, older views/favorites, missing vectors, expired
inventory, native exclusions and privacy changes during a request.

## Reviewed engagement challengers (source batch, November 15)

The shared ranker now derives a bounded engagement feature from the existing
foreground viewing-time and photo events. It requires a preceding view in the
same session/listing, caps active time at 300 seconds and distinct noninitial
photos at eight per session, uses the strongest session, and applies the existing
14-day decay inside the 30-day window. It does not change the 20/12/10/3/2/1
interest weights or reminder eligibility. Engagement's baseline ranking weight is
zero. This adds no sensor access, external-app data, SDK or consent scope.

Exposure version `:category-seeds-v1:engagement-v1` records five bounded ranking
features plus fixed category/search intent and a random response-batch ID. A
common divisor preserves the actual score differences for offline evaluation.
Training pairs come from the same shopper/session/response, and training/test
sets stay separated by shopper. Older apps remain usable; their missing features
are excluded from the new learner rather than interpreted as zero engagement.
Only exposures for the current model are eligible. Previously stored weekly
rows are retained; an existing evaluation is not silently replaced midweek.

Weekly evaluation now stores a candidate with `promoted=false`, even when the
existing evidence thresholds pass. An active authenticated administrator reviews
the before/after weights and offline accuracy in `/admin/shopping`, explicitly
confirms, then applies the stored candidate. The database validates the evidence,
current baseline and session, serializes competing reviewers, preserves unrelated
controls/catalog status, and returns the same receipt for an immediate retry.
It records a review timestamp/model version, without adding reviewer identity.
This is not an online conversion-lift claim; the stable comparison group remains.

Apply `20261115150000_shopping_reviewed_ranking.sql` only after inspecting the
current GemList schema, private table permissions and zero-gap account boundary
coverage. The migration is additive and transactional. The admin report hides the
apply control when it is absent; any other readiness failure is an error. Do not
treat this source migration or disposable-database tests as a production install.
No trained candidate was applied in this batch. Before rollout, verify the live
migration and report; to undo a reviewed ranking change, pause recommendations
and restore the evaluation's baseline weights/version through the existing
restricted operations path, then verify before resuming. Do not alter the
shopping-delivery or advertising switches as part of ranking rollout.

Validation: engagement/worker regression tests, actual member/service admin
adapters, PostgreSQL migration/authorization and concurrent-review tests, and the
actual review component at 320px and 1280px across eligible, insufficient, stale,
paused, unavailable, applied and pending states. Browser screenshots use synthetic
evaluation evidence, never private shopper activity. Required CI also runs the
PostgreSQL transaction and review-screen checks.
