# Website personalization and shopping follow-ups

Signup has required versioned Terms acceptance and one optional shopping-email/website-notification opt-in. Google onboarding records the same choices. Broader permission defaults off for existing members. Existing saved listings and requested saved-search alerts remain independent until an explicit all-shopping unsubscribe or account alert-off action. There are no frequency tiers or daily email caps.

## Release order and switches

1. Apply `20261113010000_shopper_personalization.sql` to GemList in a transaction after confirming the project and backup. It creates private, RLS-protected tables/functions and additive source-verification/notification guards. It does not backfill private browsing or opt anyone into broader email.
2. Deploy the app and verify signup, privacy withdrawal, account switching, and the private `/admin/shopping` report. Tracking, recommendations, embeddings, and weekly evaluation default enabled; shopping delivery and advertising initially remain paused.
3. Run the protected shopping sweep to build the full eligible native/catalog projection. It uses cached provider reads only; the initial catalog is not treated as new saved-search matches. Native, dealer-feed, and API completeness/availability/moderation gates remain authoritative. Missing records expire as candidates; they are never labeled sales.
4. Configure the independent public-content embedding runner. Add one identical random `SHOPPING_JOB_SECRET` to web-host secrets and the repository Actions secret, then set repository variable `SHOPPING_EMBEDDINGS_ENABLED=true`. Run `Shopping listing embeddings` manually once; its hourly schedule processes changed hashes only. It checks for work before installing/loading the model. Do not put SigLIP on the 1 GB inventory VPS.
5. Enable Shopping delivery in Admin → Analytics → Shopping performance after queue/availability/unsubscribe verification. The `bluebird-shopping` database schedule invokes the shared worker every 15 minutes using the existing authenticated job credential. The saved-search entry point delegates to the same leased worker. Related candidates within a processing window share one durable delivery; distinct windows can send on the same day.
6. Optional advertising remains paused until actual Meta/Google credentials are configured and validated. `META_PIXEL_ID`, `META_CONVERSIONS_TOKEN`, `GOOGLE_MEASUREMENT_ID`, and `GOOGLE_MEASUREMENT_SECRET` are server configuration. Only the consent-gated Meta Pixel loads in the browser; Google uses the allowlisted server adapter. Do not add automatic URL/search/form capture. Meta shares event IDs across browser/server; Google events use one server path and are not retried after an ambiguous handoff. Verified purchases use transaction IDs.
7. Register the signed Resend webhook `/api/shopping-email-events` and set `RESEND_SHOPPING_WEBHOOK_SECRET` before treating provider complaints/bounces as complete. Clicks and approximate opens work independently. Existing operational email remains separate.

Each switch is independent, including embedding compute and weekly ranking updates. Pausing does not delete saved listings. The web-host and repository secrets must never be committed or returned in reports.

## Ranking and reminders

SigLIP 2 public text/photo features are generated by the pinned `google/siglip2-base-patch16-224` checkpoint and stored as versioned 768-dimensional vectors. The worker averages normalized text/image representations and normalizes the result; unavailable photos fall back to text. Candidate vectors stay in Postgres and HNSW candidate retrieval returns only public cards/similarities. Stale hashes are excluded. There is no LLM.

Signal weights live in `SHOPPING_WEIGHTS`. Default verified purchase/inquiry/favorite/repeat/search/view weights are 20/12/10/3/2/1, with a 14-day half-life, 30-day profile window, and persistent explicit favorites. Category and home shopping mode remain separate. Explicit browse filters/sorts retain their existing authority. Private messages, identity records, and payment credentials never enter vectors or advertising.

Qualifying unchanged-item reminders start at 24 hours, 72 hours, and seven days after a favorite or repeat visits in two sessions within a seven-day window. A cycle cannot resend the same step without fresh activity. Contact pauses it seven days; purchases, dismissals, unavailability, and withdrawal suppress it. Repeated unanswered reminders are reduced independently of genuine new changes. Bluebird controls timing; these settings are not represented as competitor schedules. There is no mandatory digest.

Weekly challengers train on bounded, normalized recommendation features and source-verified inquiry/purchase outcomes. Training and evaluation split by shopper. Promotion needs at least 200 training pairs, 100 test pairs, 30 shoppers with verified outcomes, and a three-point held-out pairwise accuracy improvement. These are offline ranking checks, not a promised conversion lift. A stable 10% comparison group evaluates shopper contacts and return behavior; it keeps explicit alerts and history tools.

## Delivery and privacy guarantees

Queue uniqueness is per shopper/listing/source event. Delivery leases, recipient serialization, provider idempotency, capped retries, and per-window grouping protect against duplicates. Verified email recipients only; managed imports and synthetic addresses are excluded. Permission, individual saved searches, availability, prices, dismissals, and contacts are checked again after email rendering, immediately before provider handoff. Already accepted email cannot be recalled.

Unsubscribe is a signed-recipient-token POST with one-click headers; GET shows confirmation to avoid link-scanner unsubscribes. It atomically updates preference audit/suppression. Consent withdrawal and event writes serialize in Postgres so an in-flight batch cannot restore history. Accounts cannot read other shoppers' history, vectors, queues, consents, or analytics. Browser-characteristic hashes never establish identity or merge accounts. Precise coordinates are transient and excluded from private activity/ad payloads. Global Privacy Control suppresses advertising.

Browsing/search events expire after 90 days; recommendation profiles use 30. Explicit saves stay in their original systems. Delivery/dedup records expire after 180 days, provider outbox records after 30. Durable dismissal, trusted purchase stops, and completed reminder steps persist independently until history is cleared or consent withdrawn; guest choices expire with the guest privacy record. Email pixels are approximate; actual clicks/contacts are stronger outcomes.

## Capacity and verification

`/admin/shopping` reports current catalog/vector counts, activity/vector bytes, queue outcomes, opt-outs, provider complaints, cohort contacts, and weekly evaluations. No feature is evidence of a verified sale unless a trusted order capture or live verified-sale record exists. Inferred inventory disappearance never supplies purchase evidence.

Embedding compute is isolated from the website and inventory VPS. Jobs are bounded to 35 minutes of work/45-minute runner lifetime and 32-item writes. Model/checkpoint caches avoid repeat compute; idle runs skip model installation/loading. Catalog/notification writes and availability reads are batched. Measure actual database/vector growth and worker execution before increasing throughput. Existing listing-provider budgets are unaffected by recommendations, similarity reads, alerts, and embedding jobs.

Validation: production code tests cover browser event allowlists, trusted purchase isolation, filtering, ranking, reminder thresholds, RLS, consent audit/withdrawal, preserved saved alerts, retry deduplication, multiple deliveries per day, recipient handoff races, and rendering-time unavailability. PGlite tests substitute array distance for pgvector/HNSW; validate the actual extension/index on production or a real pgvector database before enabling vector retrieval.
